# Employee Manager

An example employee manager app

## Stack

All of these were chosen as they were recommended by the project requirements.

• Next.js 16 or with App Router, Server Components, and Route API
• TypeScript with `strict: true`
• Tailwind CSS
• shadcn/ui
• TanStack Query
• Zod
• Vitest with React Testing Library for unit and component tests
• Playwright for end-to-end tests

The only library added for DX was:

- prettier and prettier-plugin-tailwind - to keep the codebase clean and tidy

## Server vs Client components

- This app uses SSR to hydrate a client side component using the following pattern:

```jsx
async function SSRComponent() {
    const initialData = getServerData(); // data is fetch server side before entering a client-side component
    return <ClientComponent initialData={initialData} />;
}

async function ClientComponent({ initialData }) {
    const dataQuery = useQuery({
        placeholderData: initialData,
        // ...
    });
    return <></>;
}
```

- This relation can be found in:
    - Home -> EmployeeList
    - EmployeeDetails
    - EmployeeEditor
- only `employees/new` does not use this, as server-side data is not needed for producing a new employee

## Run The Project

```bash
npm run dev
```

This will run the dev environment on [http://localhost:3000](http://localhost:3000)

## Run Tests

```bash
// runs vitest unit/component tests
npm run test
// runs playwright e2e tests
npm run test:e2e
```

## Figma Gaps

The Figma did not match project requirements, but overall styling was taken from the Figma style guide and transferred into usable TailwindCSS tokens.

A list-specific search bar and clear 'New Employee' button were missing, as well as overly verbose candidate information page which did not meet project specification. In these cases, the layouts were improvised.

## AI Usage

AI played a major role in getting this project completed in time.

### The Good

- Mock data generation - `generate-employees.mjs` and most API routes were generated by Copilot, as they are not the focus of this excercise.
- npm resolution - `vitest` and `@testing-library` had depedency collisions which Copilot was able to solve in 20 minutes - better it than me.
- Test generation - due to inexperience with the test suite, I initially used ChatGPT for guidance on how vitest and playwright are written and utilized, plus summarizing documentation on them.

### The Bad

- Bias towards default tailwind styles resulted in generated screens with default colours, these were promptly rejected
- Improper usage of APIs resulting in screens calling the JSON directly, and failure to identify proper SSR usage pattern

## Trade-offs

- Proper Toasts for editing/creating employees
- A proper API for testing updates to the employee data
- Light/Dark mode - currently its dark only

## Self-Review

- Code Organization - given the time limit, many stray/duplicate functions and types exist which should be organized into /lib or .type files
- More comprehensive components - many duplicate components exist, could probably be worth investing in refactoring
- Better component breakdown - many components are way too large, could benefit from breaking into individual components (that said, there many not be much reusability given the project scale)
